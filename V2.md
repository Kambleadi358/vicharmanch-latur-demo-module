# Vicharmanch V2 — Final Production Certification Audit

**भारतरत्न डॉ. बाबासाहेब आंबेडकर विचारमंच, लातूर**
Audit date: **1 August 2026** · Auditor: Lovable engineering audit pass · Scope: full V2 Community Operating System
Method: **measured**, not assumed — build output, live browser run, database queries, automated security scan.

---

## 1. Executive Summary

Vicharmanch V2 is a genuinely large, genuinely functional community platform. 141 TypeScript/TSX files, ~23,600 lines, 36 database tables, 10 edge functions, 25+ admin modules, a full Marathi public UI. The production build succeeds in 11.7s with 19 lazy-loaded route chunks. Every public route renders in under 900 ms on a throttle-free mobile viewport.

It is **not** production-certified today. Four **error-level** security findings were confirmed by scan, and three of them are exploitable by an anonymous visitor with nothing more than a browser console:

1. Quiz **answer keys are publicly readable** before and during the quiz.
2. **Any anonymous user can read and UPDATE any quiz session** — including `score`, `status`, participant name, date of birth and IP address.
3. **Any anonymous user can read and modify any quiz answer row.**
4. **Voter phone numbers and device fingerprints are publicly readable** from `public_votes`.

Additionally, one module previously reported as planned — the **Dynamic Winner Engine** — does **not exist in the codebase or the schema**. `program_winners` still carries hardcoded `first_place` / `second_place` / `third_place` columns and there is no `program_rank_definitions` table and no `rank_id` reference anywhere in `src/` or `supabase/`.

Automated test coverage is **effectively zero**: one placeholder test (`expect(true).toBe(true)`) across a 23,600-line codebase.

**Verdict: NOT production-certified.** The gap is narrow and well-understood — roughly 1–2 focused days of work — but it is real, and the findings are of the class that would let a motivated participant win the quiz and harvest voter phone numbers.

## 4. Testing Summary

- `tsgo --noEmit`: **0 errors**.
- `vite build`: **succeeds**, 11.69 s.
- **Caveat:** 90 occurrences of `as any` in `src/`. These are compile-time escape hatches around tables missing from generated types; each one is an un-typechecked database access path.

### 4.2 Unit testing — **FAIL**
```
Test Files  1 passed (1)
     Tests  1 passed (1)
```
The single test is `src/test/example.test.ts` → `expect(true).toBe(true)`. **There are no tests for any business logic** — not for donation totals, vote weighting (3·1st + 2·2nd + 1·3rd), quiz scoring, archive summaries, or rank ordering. Measured coverage of application code: **0%**.

### 4.3 Integration / System testing — **PARTIAL (manual only)**
Verified live in a headless Chromium at 393×800 (the user's actual viewport). All 9 public routes returned HTTP 200 and rendered. No route crashed. No error boundary triggered.

### 4.4 Regression testing — **FAIL (no harness)**
There is no automated regression suite. Every change to date has been validated by typecheck + build + eyeball. For a platform holding financial records, this is the single largest process risk.

## 11. Security Summary

### Error-level (must fix before public event)

| # | Finding | Table | Exploit |
|---|---|---|---|
| 1 | **Quiz answer keys publicly readable** | `quiz_questions` policy *Anyone can view questions* | Any visitor reads `correct_answer` for every question at any time, regardless of quiz status |
| 2 | **Anonymous read + UPDATE on all quiz sessions** | `quiz_sessions` — *Anyone can read/update sessions*, `USING (true)` | Exposes name, DOB, IP, user agent, score; allows tampering with `score`, `current_index`, `status` |
| 3 | **Anonymous read + UPDATE on all quiz answers** | `quiz_answers`, condition `true` | View or rewrite any participant's answers and `is_correct` flags |
| 4 | **Voter phone numbers exposed** | `public_votes` — *Public read votes* | `voter_phone` and `device_fingerprint` readable by anyone |

### Warn-level (34 findings)
- Leaked-password (HIBP) protection **disabled**.
- ~14 `SECURITY DEFINER` functions executable by any signed-in user.
- Multiple `USING (true)` / `WITH CHECK (true)` write policies.
- `participation-songs` bucket accepts arbitrary uploads with no ownership or file-type validation.
- `homes` / `home_donations` / `archives` expose contact and financial detail publicly (partly intentional under the transparency mandate — but `contact_phone` is not).
- 11 functions with mutable `search_path`.

### What is correct
- Roles isolated in `user_roles` with `has_role()` — no escalation path.
- Judge credentials never leave the server.
- RLS enabled on all 36 public tables; GRANTs present.
- Service-role key never referenced in client code.

## 20. Final Conclusion

Vicharmanch V2 is a real Community Operating System, not a demo. The transparency architecture, the audit trail, the archive system, the registry-as-source-of-truth model, and the entirely Marathi interface reflect the movement's values faithfully. Twenty-two of twenty-five modules are complete and working.

But an audit that reports 100% here would be dishonest. A participant can currently read the quiz answer key from their browser, rewrite their own score, and scrape voter phone numbers — all without logging in. The Dynamic Winner Engine was scoped and never built. And 23,600 lines of code carrying the community's financial records are protected by exactly one test that asserts `true === true`.

None of this is hard to fix. It is one to two days of focused work for the blocking items. But until that work lands, the honest answer is the one below.
